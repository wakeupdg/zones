# SPK-008: stacked identical windows, first frame sample after the first dragged event

Run: October 24, 2026, about 2:10 AM PT, macOS 27.0.1 (26A434), one display. Probe: `Spikes/WindowIDProbe` subcommand `spk008` (default mode) and `spk008 --single`.

**Verdict: PASS for the CG description source (20 of 20); FAIL for the AX source at the first tick (0 of 20), PASS for AX at the first changed tick (20 of 20, caveat below).** Overall for the spec wording: PASS on CGWindowListCreateDescriptionFromArray, with two conditions the AC-056/AC-057 expectations must carry (see consequence).

## Method

- Four titled NSWindows of one pid, identical size and origin, titles "stack-0".."stack-3" (the probe's own). A balanced shuffled order picks which window is raised to the front each trial; the top window is confirmed from the CG on-screen list (front to back).
- Mouse down on the top window's title bar (12 pt below its top edge), then the first `leftMouseDragged` (+40, +25 pt). All events are posted from a driver thread (the title-bar mouse-down puts AppKit into a drag tracking loop on the main thread).
- Samples at 60 Hz ticks (16.7 ms apart) from the first dragged event: one `CGWindowListCreateDescriptionFromArray` read of the four ids (matched by `kCGWindowNumber`) and one AX read of all four windows (250 ms messaging timeout, matched by the probe's own titles). A candidate "changed" if its origin moved more than 0.5 pt from the pre-drag baseline.
- Default mode: after the first dragged event, a 125 Hz stream of dragged events follows (like a real mouse). `--single` mode: the first dragged event only.

## Caveats

- Events are synthetic (CGEventPost). The probe and the dragged windows share one process, so the AX server for those windows runs on the main thread that is inside AppKit's drag tracking loop. The AX lag (tick 6 to 7) is probably inflated by that and must be re-measured against another process; SPK-016's child-window mode is the place. Do not read it as the AX lag of a foreign app.
- One display, one Space, one pid. The stack has no differing sizes, so "identical" here means pid, size and origin all equal.
- A single dragged event moves nothing: AppKit takes the first dragged event as the drag start and the window follows from the second event on. A real mouse sends many; a test harness that posts exactly one will see no move.

## One-line consequence

Resolve the dragged candidate of identical stacked windows from a CG description sample (match by `kCGWindowNumber`) taken at least one 60 Hz tick after the SECOND dragged event, and it is always the top window of the stack (20 of 20); do not use an AX frame sample at the first tick for this (0 of 20), so AC-056/AC-057 should confirm on the CG sample and let AX confirm later; T14 and T21 must not treat "the first dragged event moved the window" as a precondition.
