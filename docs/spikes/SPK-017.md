## What the host run shows and does not show

- Present: `kCGWindowNumber`, `kCGWindowOwnerPID`, `kCGWindowLayer`, `kCGWindowBounds` were present on every entry (`missing(bounds=0 layer=0 pid=0 number=0)`, 22 entries, 13 at layer 0). This is a necessary condition only, because the host has Screen Recording granted.
- NOT shown: nil names. With Screen Recording granted, `kCGWindowName` was non-nil on 22 of 22 entries (17 non-empty) and `kCGWindowOwnerName` non-nil on 22 of 22. The denied behavior (nil or empty names, owner-name behavior on 26 vs 27) was NOT reproduced. TCC was not changed.
- Resolution (pid plus frame): only the pure logic was exercised, on fabricated lists (`SYNTHETIC-LOGIC resolver self-test: PASS`: candidates are layer-0 windows containing the point; the moved window is found by pid and size without ids or names). A real dragged-window run needs a human. The one real resolution attempt (mouse-up after 1 dragged event, non-human source) printed `RESOLVED pid=nil id=nil byField=false byPidFrame=false movedCandidates=0`, i.e. no window moved, as expected for a no-op drag; it is not evidence either way.
- Not verified: whether `mouseEventWindowUnderMousePointer` agrees with the pid plus frame result on a real drag (`byField`).

## Expectations for downstream tickets (conditional on the clean rows)

- T14 CGWindowEnumerator: use only number, owner pid, layer, bounds. Do not depend on `kCGWindowName` or `kCGWindowOwnerName` (use `NSRunningApplication(processIdentifier:)` for bundle id).
- AC-056: candidates resolve by pid plus frame, never by title.
