# SPK-016: CG description polling as the move-confirmation source

Run: October 24, 2026, about 2:30 AM PT, macOS 27.0.1 (26A434), one display, AX trusted. Probe: `Spikes/WindowIDProbe` subcommand `spk016` (4 full runs; run 4 is the primary table, runs 1 to 3 are shown for stability). The target is a CHILD PROCESS (`--child-window`), so the AX numbers here are cross-process.

**Verdict: FAIL on the predeclared criterion; AX frame polling stands (ADR-0006 unchanged). No ADR is proposed.**
Move confirmation passes (20 of 20 at sample 1). The cost leg fails only on a latency-delta criterion fixed before the run, by small absolute margins (see "How close"). Polling never errored, never blocked, and never touched the stopped app, which is the point of the alternative.

## Method

- Parent polls `CGWindowListCreateDescriptionFromArray([id])` at 60 Hz (16.67 ms ticks), matching by `kCGWindowNumber`. No names are requested.
- Part A: parent writes a `move +-25 0` command to the child, then counts ticks until the origin differs (20 trials, alternating direction). AX position read (250 ms timeout, ADR-0015) taken at the same ticks for contrast.
- Part B: 5 s of polling (300 samples) live, then `kill -STOP` (confirmed with `ps` state T), 5 s of polling, 3 AX reads, `kill -CONT`, a recovery move, 5 s of polling again. The child is continued on every exit path (defer plus SIGINT/SIGTERM/SIGHUP handlers); `pgrep -fl WindowIDProbe` shows nothing after each run.
- Predeclared cost criterion: zero errors, zero origin changes, and stopped p50 and p95 each at most 2x the live value (floors 1 ms and 2 ms).

A stopped app costs the AX path 250 ms per read (ADR-0015: at most 0.5 s on the serial actor with the one retry); the description path cost about 0.6 ms at p50.

## How close was the cost criterion

- Against the 2x rule: stopped p50 over live p50 was 2.7x, 1.3x, 2.5x, 1.4x (runs 1 to 4); stopped p95 over live p95 was 1.0x, 3.5x, 1.7x, 4.5x. The rule failed in 4 of 4 runs (run 1 on p50, run 2 on p95, run 3 on p50, run 4 on p95), so the verdict is FAIL.
- Context: the host was a busy shared machine. Live p95 itself moved from 0.8 ms to 3.4 ms between runs and the post-CONT live phase reached p95 6.4 ms and max 75.8 ms. Absolute stopped numbers stayed at p50 under 1.5 ms, p95 under 3.8 ms in every run, well inside the 16.7 ms tick.
- So the data do NOT show the polling hanging or erroring on a stopped app (the property that matters for AC-078); they show a small, noisy latency rise that this criterion treats as a fail. The orchestrator may reasonably re-run on a quiet host with a noise-aware criterion before deciding; this file does not re-grade after the fact.

## Caveats

- Child windows are moved by `setFrameOrigin` on command, not by a user drag. A real drag also runs the target's tracking loop, which may delay AX replies further (SPK-008 saw this same-process) but does not affect the description path.
- One display, one Space, macOS 27.0.1 only (the SPK has no per-OS requirement).
- Description polling confirms where the window server says the window is; it cannot see a window the app refuses to move (AC-055) any better than AX can.

## One-line consequence

AX frame polling stands for move confirmation (ADR-0006 unchanged); CG description polling is a viable, hang-proof secondary signal (20 of 20 at sample 1, never blocked by a stopped app), so T21 may use it to short-circuit a hung target (AC-078) without waiting 250 ms, but that use is not an ADR.
