# SPK-010 Write protocol app matrix

Result: PARTIAL (needs-human items)

Everything the probe can measure is recorded. Not run: IntelliJ (not installed), all VoiceOver-on passes, animation observation, VoiceOver survival (human-only, listed at the end).

## Method

- Tool: `Spikes/WriteProbe` (standalone SPM CLI, probe-local mirror of FrameWriting; imports no Zones target). Per Snap: 250 ms AX messaging timeout (ADR-0015), read `AXEnhancedUserInterface`, size, position, size writes, read back, delta = readBack - target, retry once on timeout (a second consecutive timeout aborts).
- Target window: first `AXStandardWindow` (focused, else first of `AXWindows`). Target rect `120,120,900,600`; each run alternates target and the window's original frame; the original frame is written back at the end of every run set (`frame restored: yes` in every row).
- Per app, 3 passes of 10 runs: A `toggle`; B `leave`; C `toggle` with `AXEnhancedUserInterface` seeded true by the probe (`--seed-eui`), a VoiceOver-off stand-in. The prior value is put back afterwards. Pass C is NOT a VoiceOver run.
- Driver: `Spikes/WriteProbe/run-matrix.sh`. Raw JSON lines: `docs/spikes/SPK-010-matrix-runs.txt` (about 1:58 AM PT), small-target probe `docs/spikes/SPK-010-small-target-runs.txt` (2:02 AM PT), SIGSTOP runs `docs/spikes/SPK-010-sigstop-runs.txt` (1:59 AM to 2:00 AM PT).
- macOS build: Darwin 27.0.0 (host as run). All apps were the user's real installs; windows were moved and restored.

Read-back quirks:

- Calculator: size is not settable; both size writes return AXError -25200 (kAXErrorFailure), the position write succeeds. The Snap must not stop at the first refused size write.
- Chrome, first run of the session (log not kept): its only window was fullscreen on another Space. `AXWindows` was empty, `AXFocusedWindow` returned it with `AXFullScreen=1`, `AXPosition` settable=false, the position write returned -25200, the size write returned success. The window was restored.
- `AXEnhancedUserInterface` set returns AXError -25208 (kAXErrorActionUnsupported/NotImplemented) in every app tried, yet the value changes (read-back false after the off-write, true after the restore-write). Success must be judged by read-back.

## Consequences

- AC-071: in all 8 apps the accepted size was larger than the Zone target at least once and the top-left stayed aligned after size, position, size. Zero follow-up position writes were needed on this OS. Keep the rule as a guarded defensive path (one extra position write only if the read-back top-left is off by more than 1 pt); tests with fakes stay valid, and no real-app test should expect the follow-up to fire.
- AC-075 (manual): not satisfied or refuted. With VoiceOver off, Chrome, VS Code and Slack Snaps all returned applied or clamped within 151 ms (max), with Enhanced UI toggle and leave behaving the same in the AX data. Whether motion is visible, and whether VoiceOver still speaks after ten Snaps, needs a human (steps below). Do not mark AC-075 done from this spike.
- AC-075 / ADR-0022 implementation: because the Enhanced UI set returns -25208 while taking effect, FrameWriting must (a) read the value first, (b) set false only when it is true, (c) re-read and treat the read-back as truth, and (d) restore with a read-back check. Treating -25208 as failure would skip the restore and leave the app in the wrong state. This is exactly what happened in the stopped-app run (below).
- AC-078 (write-path part): a stopped app costs 2 x about 253 ms = about 0.5 s of writes, one retry, then abort, and queued writes did not apply after `kill -CONT` (frame unchanged). But the Enhanced UI read in front of the writes is a third 250 ms timeout, so the whole Snap took about 0.76 s (not 0.5 s). To meet "at most about 0.5 s", count the EUI read as the first timeout (a timeout there is the first strike; the next write is the only retry), or skip the EUI read when AppHealth already marks the app unresponsive. The frame-count parts of AC-078 still need the real app and a screen recording.
- ADR-0022 recovery record: with the EUI seeded true and the app stopped, the restore write timed out and the attribute stayed true after `kill -CONT` (recovered by hand). So the once-per-app recovery record with the prior value is necessary: drain it on the next successful AX contact with that app, not only on Quit.
- ADR-0015 retry: Finder alone timed out once organically (first attempt 254 ms on a large resize, retry succeeded in 132 ms), so retry-once is not just a hung-app path. Median Finder Snap is 180 to 215 ms, close to the 250 ms budget; Finder is the likeliest app to hit an unresponsive cooldown when busy.
- Windows to skip: fullscreen windows refuse position writes; check `AXFullScreen` and the settable flags before a Snap.
