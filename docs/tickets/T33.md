# T33: Onboarding window: Accessibility explanation, System Settings button, cheat sheet, badge and Grant Accessibility wiring

Kind: build. Blocked by: T20 (PermissionMachine), T32 (Settings General pane, owns key caps). Estimate: 90000 tokens. Branch: ticket/T33. Protocol: none (consumes PermissionProbe). Fake: FakePermissionProbe, if a view-model test needs it.

## Goal

- One SwiftUI onboarding window, shown by `PermissionEffect.showOnboarding` and closed by `.dismissOnboarding`. Exactly one such window ever exists; a second `showOnboarding` orders the existing one front.
- Page 1 explains why Accessibility is needed and has a button that calls `PermissionProbe.openAccessibilitySettings()` (Privacy & Security > Accessibility), plus a status line that follows `PermissionState`.
- In `revoked` the window offers "Open System Settings". "Quit and Reopen" appears ONLY in `needsRelaunch`, with a one-sentence explanation that Zones must restart to regain the grant. Never in `revoked`, never in `notGranted`.
- Last page lists the three gestures (hold Shift to see Zones; add Control to Span; Control+Option+N to send) with key caps that redraw when the Activation Modifier (or Span Modifier) changes in General.
- The status item badge binds to `StatusItemModel.badged`; the "Grant Accessibility" menu item binds to `MenuItem.grantAccessibility` from `MenuModel.build`. On the launched-at-login path no window appears in any state; badge and menu item stand in.

## Acceptance

### AC-005 (manual) — Grant noticed without relaunch

Covers: US-003

### AC-020 (manual) — Cheat sheet and key caps

Covers: US-012
Verify: Walk onboarding to its last page; change the modifier; observe the key cap.

Related stories (context only): US-005 (revoked window offers "Open System Settings"; "Quit and Reopen" only after 3 failed recreations over 10 s with probe true), US-008 (launched at login: no window, only badge and "Grant Accessibility" menu item).

- 0008 Activation modifier defaults to Shift, span modifier to Control; both user-selectable.
- 0010 Default shortcuts use Control+Option (the "send to Zone N" gesture).

## Design decisions (already made, do not reopen)

- Pure view state: `OnboardingViewState.derive(_ p: PermissionState, relaunchOffered: Bool) -> OnboardingViewState` with fields `statusLine: String`, `showOpenSettings: Bool`, `showQuitAndReopen: Bool`, `relaunchExplanation: String?`, `windowVisible: Bool`.
  - notGranted: status "Waiting for Accessibility access", Open System Settings shown, no relaunch.
  - revoked: status "Accessibility access was turned off", Open System Settings shown, no relaunch.
  - needsRelaunch: status "Zones can't recover Accessibility without restarting", relaunch shown with explanation "Zones must quit and reopen to pick up the restored Accessibility permission.", Open System Settings still shown.
  - granted and suspect: `windowVisible` false (window is dismissed by the effect, not by the view).
- The window has two pages: page 1 Accessibility, page 2 cheat sheet (the last page). Next/Back are always enabled, so the cheat sheet can be reached while still ungranted. Dismissal closes whichever page is showing.
- The window never calls `AXIsProcessTrusted` itself; polling belongs to PermissionMachine. The button calls only `probe.openAccessibilitySettings()`.
- "Quit and Reopen" action: relaunch the app bundle (`NSWorkspace.openApplication` on `Bundle.main.bundleURL` with `createsNewApplicationInstance`) then `NSApp.terminate(nil)`. Keep it in the controller behind a closure so it is injectable.
- Key caps observe Preferences changes through whatever observation API T32/the store already exposes (grep `activationModifier` in App/). Do not add a second source of truth; if there is only the `zones.preferences` UserDefaults blob, observe `UserDefaults.didChangeNotification` and decode with `PreferencesCodec`.
- Window frame: fixed size around 480x360, not resizable, title "Welcome to Zones", centered on the Display under the cursor is optional.

## Test plan
