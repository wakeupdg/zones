# T47: QA fix: Settings tab bar visible at default width; Cmd-W, Delete and Clear labels on the Shortcuts recorder

Kind: fix (QA round 2). Blocked by T42, T34, T32 (all done). Estimate 80k tokens. Protocol: SettingsWindow, KeyCapturing, RecorderKeyMap (edit). Fake: none needed (AppKit view tests).

## Goal

- At the default and the minimum Settings window size, every pane tab (General, Layouts, Shortcuts, Appearance, Exclusions, About) is visible in the toolbar, none in the overflow (`>>`). Raise the default and minimum content width as needed (and SettingsView `.frame(minWidth:)`), or shorten labels; keep the window placement on the cursor Display (AC-021).
- Cmd-W closes Settings when a shortcut recorder is first responder but not recording; while recording, Cmd-W is still captured as a chord candidate as today. Expose `isRecording` on `KeyCapturing` and check it in `SettingsWindow.performKeyEquivalent`.
- Delete (keyCode 51) and Forward Delete (117) with no modifiers on a focused recorder clear that action's shortcut (idle or recording), through the same path as the Clear button.
- Each Clear button reads `Clear <action name>` to VoiceOver (accessibilityLabel), and each Accept button `Accept <action name>` if present.

#### QA-2.2: Cmd-W does not close Settings while a shortcut recorder has focus, even when it is not recording; on the Shortcuts tab the window opens with recorder 1 focused
- Where: `App/Settings/SettingsWindow.swift:8`
- Evidence: Code: SettingsWindow.performKeyEquivalent has `if firstResponder is KeyCapturing { return super.performKeyEquivalent(with: event) }`. The comment says this should apply only while the recorder records, but the check fires whenever a RecorderField is first responder. The idle recorder's handle() then returns .passThrough for Cmd-W (RecorderKeyMap: not recording, modifiers present), so nothing closes the window. Dynamic proof, scratch suite QaA11yR2.closeKeysControl, same key path for both cases (log qa/round2/accessibility/run6.log): `AXR2-CLOSE tab=general key=Cmd-W firstAtOpen=SettingsWindow closes=1` vs `AXR2-CLOSE tab=shortcuts key=Cmd-W firstAtOpen=RecorderField closes=0 visible=true`. In recorderKeyboard (run5.log), after a recorder has been used and is idle again: `cmdWOnIdleRecorder closes=0`. With a window opened on Shortcuts, the initial first responder is `Recorder(Shortcut for Send to Zone 1)`.
- Repro: Settings > Shortcuts: click a recorder (or Tab to it), press a chord so it is captured (recording ends, focus stays). Then press Cmd-W: the window stays open. In-process: put /private/tmp/claude-501/-Users-dganesh--MY-PROJECTS-open-source-clones-fancy-zones/faae5a4c-2276-4507-97e4-667cc6d49ef2/scratchpad/qa/round2/accessibility/QaA11yR2Tests.swift into AppTests of a worktree, run `xcodegen generate`, then `Q_LOG=<f> scripts/q.sh xcodebuild -project Zones.xcodeproj -scheme Zones -configuration Debug -derivedDataPath .build/DerivedData CODE_SIGN_IDENTITY="Zones Dev" "-only-testing:AppTests/QaA11yR2/closeKeysControl()" test` and grep AXR2-CLOSE.
- Fix hint (verifiers kept it 3/3): Bypass Cmd-W only while the recorder is recording: expose `isRecording` on KeyCapturing (or RecorderField) and check `(firstResponder as? KeyCapturing)?.isRecording == true`.

#### QA-2.3: Shortcuts pane: all 14 Clear buttons are announced only as 'Clear', with no action name and no title element (link lost when T42 dropped LabeledContent)
- Where: `App/Settings/ShortcutsPane.swift:68`
- Evidence: Walked the real AX tree with the AX API on the test host's own pid (AXIsProcessTrusted()=true): run2.log/run7.log show 14 lines like `AXR2-DET clear desc=Clear title=- titleEl=- help=- linked=-`. By contrast, the Layouts pane 'Duplicate' and the Exclusions pane 'Remove' buttons report titleEl=true, because LabeledContent links them to their row label. `git show 8c79dc5` (T42) replaced `LabeledContent(name) { HStack { recorder; Button("Clear") } }` with a bare `HStack { Text(name); Spacer(); recorder; Button("Clear") }`, which drops the AXTitleUIElement link. The 'Accept' button on line 73 has the same problem. In the VoiceOver rotor's buttons list you get 14 identical 'Clear' entries.
- Repro: Run the scratch suite `-only-testing:AppTests/QaA11yR2/details()` (same file and command as above) and grep `AXR2-DET clear`. Or turn on VoiceOver, open Settings > Shortcuts, VO-U and open the Buttons rotor: 14 entries read just 'Clear'.
- Fix hint (verifiers kept it 2/3): `Button("Clear") {...}.accessibilityLabel("Clear \(name)")` (and `Accept \(name)`), or keep LabeledContent and fix the alignment another way.

#### QA-2.5: Delete does not clear a shortcut from the recorder: while recording it beeps and is rejected, and while idle it does nothing (T42 Goal says 'Delete clears')
- Where: `Sources/ZonesWindowing/Settings/RecorderKeyMap.swift:34`
- Evidence: disposition(): when recording, keyCode 51 (Delete) is not in the key table, so it returns .reject (NSSound.beep). When not recording, it returns .passThrough. No code path calls model.clear. Dynamic run (run5.log): `afterDeleteWhileRecording ... value=Type shortcut` (still recording, nothing cleared) and `afterDeleteIdle first=Recorder(Shortcut for Send to Zone 1)=⌃⌥1` (chord unchanged). T42 brief Goal: 'Keyboard-only: Tab reaches each recorder; Space/Return starts recording; Escape cancels; Delete clears'. Tab, Space and Escape do work: Tab moves recorder 1 to 2 to 3, Shift-Tab goes back, Space shows 'Type shortcut', Escape restores the chord.
- Repro: `-only-testing:AppTests/QaA11yR2/recorderKeyboard()` and grep AXR2-REC. Live: Settings > Shortcuts, Tab to a recorder, press Delete (or Space then Delete): the chord stays.
- Fix hint (verifiers kept it 2/3): Add a `.clear` disposition for keyCode 51/117 with no modifiers (recording or focused idle) that calls onClear, which the row wires to model.clear(action).
