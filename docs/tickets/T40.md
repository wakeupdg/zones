# T40: QA fix: onboarding buttons, safe Quit and Reopen, template status-item image

Kind: fix (QA round 1). Blocked by T33, T36 (all done). Estimate 70k tokens. Area: App/Onboarding, App/StatusItemController.swift. Protocol: StatusItemController, OnboardingWindowController (edit). Fake: closure seams for openApplication and terminate.

## Goal

- Back is `.disabled` on page 1 and Next is `.disabled` on page 2 (or hidden); no opacity dimming of an enabled control.
- `relaunchApp` terminates only when `openApplication` returns an app and no error; on error it logs (category `.app`), keeps Zones running, and keeps the Quit and Reopen offer standing.
- The status-item `button.image` is a template image (`isTemplate == true`) in every state, so the menu bar tints it. The red badge is drawn as a separate non-template layer or subview on the button, shown only when the model is badged. The accessibility description stays as it is today.

## QA findings this ticket closes (verbatim evidence)

#### QA-1.0: Onboarding Back/Next buttons are drawn dimmed (opacity 0.4) while still enabled
- Where: `App/Onboarding/OnboardingView.swift:21`
- Evidence: App/Onboarding/OnboardingView.swift:21-26: `Button("Back").disabled(false).opacity(model.page == .accessibility ? 0.4 : 1)` and `Button("Next").opacity(model.page == .cheatSheet ? 0.4 : 1)`. Render scratchpad/qa/round1/screens/png/onboarding-p1-needsRelaunch-light.png shows Back at 40% (looks disabled) on page 1; it is clickable and re-sets page 1. HIG: a control that looks disabled must be disabled; a dimmed-but-enabled control is exactly the brief's checklist item.
- Repro: Open the onboarding window (first launch, not trusted); page 1 shows a greyed Back that still responds to clicks; go to page 2: Next is greyed but still responds.
- Fix hint (verifiers agreed 2/3): Use `.disabled(model.page == .accessibility)` for Back and `.disabled(model.page == .cheatSheet)` for Next, or hide the inapplicable button, instead of opacity.

#### QA-1.8: "Quit and Reopen" terminates the running app even when the relaunch fails (completion ignores the error)
- Where: `App/Onboarding/OnboardingWindowController.swift:107`
- Evidence: App/Onboarding/OnboardingWindowController.swift:104-110:
  static func relaunchApp() {
    let configuration = NSWorkspace.OpenConfiguration()
    configuration.createsNewApplicationInstance = true
    NSWorkspace.shared.openApplication(at: Bundle.main.bundleURL, configuration: configuration) { _, _ in
      DispatchQueue.main.async { NSApp.terminate(nil) }
    }
  }
The completion handler discards both the NSRunningApplication and the Error and unconditionally calls NSApp.terminate(nil). When openApplication fails (error != nil, app == nil) the only running Zones instance quits and nothing replaces it. This is the default `relaunch:` closure wired at line 21 and the model's `quitAndReopen` action behind the needsRelaunch button (rendered in scratchpad onboarding-p1-needsRelaunch.png). docs/tickets/T33.md:106 only says 'relaunch the bundle ... then NSApp.terminate(nil)'; the QA brief requires the path not to terminate when relaunch fails.
- Repro: Code trace (cannot be driven live: needsRelaunch needs a trusted app with a dead tap, and Accessibility cannot be granted on this host). To reproduce with the app: reach needsRelaunch (3 failed tap recreations over 10 s with the probe true), make the launch fail (e.g. move/rename Zones.app after launch so Bundle.main.bundleURL no longer exists, or any Launch Services refusal), press "Quit and Reopen": the completion fires with a non-nil error and the app terminates anyway; `pgrep -x Zones` then returns nothing.
- Fix hint (verifiers agreed 3/3): Inspect the completion arguments: terminate only when `app != nil && error == nil`; on error keep running, log it (category .app) and leave the Quit and Reopen offer standing (or surface the error in the status line).

#### QA-1.9: Status item NSImage is explicitly non-template (image.isTemplate = false) while AC-018 states the image is a template image
- Where: `App/StatusItemController.swift:94`
- Evidence: App/StatusItemController.swift:94 `image.isTemplate = false` (the glyph is hand-tinted with NSColor.labelColor inside the drawing handler, lines 79-86). In-process check in a scratch AppTests suite (throwaway worktree, xcodebuild test, log scratchpad/qa/round1/onboarding/xcodebuild-scratch5.log lines 171/173): `QA_MARK statusIcon badged=true isTemplate=false ... a11y=Zones, needs Accessibility access` and `QA_MARK statusIcon badged=false isTemplate=false`. The model says otherwise: Sources/ZonesWindowing/Shell/StatusItemModel.swift:7 `isTemplate: Bool = true` and StatusItemModelTests.badgeTable passes on the model alone. docs/LOCKED-SPEC.md:284 / docs/tickets/T29.md:32 AC-018: 'and its image is a template image.' The badge (red dot, 458-475 red pixels at 4x) and the labelColor glyph do render (iconprobe-*-direct8x.png; glyph is white@0.85 because this host is in Dark appearance).
- Repro: In any AppTests case: `StatusItemController.icon(badged: false).isTemplate` is false (and for badged: true). Or read App/StatusItemController.swift:94.
- Fix hint (verifiers agreed 3/3): Either amend AC-018's wording to 'drawn in labelColor with a red badge' (the red dot cannot survive template tinting), or render the glyph as a template image and overlay the badge as a separate non-template layer/attachment so the menu bar can tint the glyph itself.
