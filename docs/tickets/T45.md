# T45: QA fix: top-edge cursor resolves to its Display; suspended Span secondary stays on the Span's Display (LI-009, AC-036, AC-085)

Kind: fix (QA round 1). Blocked by T39, T26, T37 (all done). Estimate 90k tokens. Area: Sources/ZonesLayout/HitTest.swift, Sources/ZonesWindowing/Drag, Overlay model. Protocol: HitTest, Highlight, SpanLogic, OverlayModel (edit). Fake: none needed (pure).

## Goal

- `HitTest.display(at:in:)` returns the Display for a point on the top edge of the top-most Display (y == frame.maxY after the flip) and, when no frame contains the point, falls back to the nearest Display by edge distance (a cursor is always on some Display). Interior half-open tie rules between adjacent Displays stay as they are.
- A mouse-up at such a point snaps (or restores) exactly as the highlight showed (LI-009).
- While a Span is suspended (cursor on Display B, Span on Display A), the Overlay draws the Span's Zones dimmer on Display A's panel and the cursor Zone on Display B. Give `Highlight` the Span Display for the secondary set (for example `secondaryDisplay: DisplayKey?`), set it in `SpanLogic`, and make `OverlayModel.apply` paint the secondary set on that Display's panel. Update CONTRACTS.md section 3.1/3.5 for the new field.
- Update every `Highlight(` construction and pattern; T37 invariants (ReducerInvariantTests) must stay green with no new hold-out.

## QA findings this ticket closes (verbatim evidence)

#### QA-1.11: Cursor pinned at the top edge of a Display resolves to no Display: highlight goes dark and mouse-up neither snaps nor restores
- Where: `Sources/ZonesLayout/HitTest.swift:31`
- Evidence: HitTest.swift:30-32 `halfOpenContains` requires `p.y < r.maxY`. EventTapInputSource.swift:206 converts the CG event location with CoordinateSpace.appKitRect (CoordinateSpace.swift:19: y = primaryFrame.maxY - (ax.y + height)), so a CG cursor y of 0 (the cursor resting against the top edge of the primary Display, where macOS clamps it) becomes y == primaryFrame.maxY, which the half-open test rejects. SpanLogic.swift:30-32 then yields Cursor(display: nil, hit: .none); DragSessionReducer.swift:170-174 on mouseUp with display nil returns `.idle` with only hideOverlay and a log ('drop outside the arm snapshot'), no snap and no restore, although the point is on the primary Display known to the snapshot. HitTest.hit (HitTest.swift:14) is closed (`<= v.maxY`), so the Zone would have matched had the Display been found. T12 ledger/STATUS.md:41 recorded 'display(at:) is half-open at the top edge'; still true. Live drag not possible here (no Accessibility grant); MenuController.swift:57 uses the same call with NSEvent.mouseLocation.
- Repro: Scratch test: let snap = TopologySnapshot with one Display frame CGRect(0,0,1920,1080); HitTest.display(at: CGPoint(x: 960, y: 1080), in: snap) == nil (expect the Display). Or: EventTapInputSource.translate(type: .leftMouseUp, event: CGEvent at location (960, 0), primaryFrame: CGRect(0,0,1920,1080)).point.y == 1080, then drive the armed reducer with mouseUp at that point with the Activation Modifier down: effects == [.hideOverlay, .log(...)] and no .snap.
- Fix hint (verifiers agreed 3/3): Treat the top edge as closed in halfOpenContains (p.y <= r.maxY when r is the top-most Display, or clamp the flipped y to nextDown(maxY) in translate), and fall back to the nearest Display by edgeDistance when no frame contains the point.

#### QA-1.12: Suspended Span's secondary highlight is painted on the cursor's Display using the Span Display's Zone numbers
- Where: `Sources/ZonesWindowing/Drag/SpanLogic.swift:80`
- Evidence: SpanLogic.swift:76-80: while `span.suspended` (cursor Display != span.display), Drop is built with `display: cursor.display` and `secondary: span.zones` — the Zone numbers belong to span.display's layout. Highlight has a single `display` (DragTypes.swift:7-11). OverlayModel.swift:72-80: `active = !h.dimAll && h.display == panel.display` and secondary fill is applied only when `active` and `h.secondary.contains(zone.number)`, i.e. on the cursor's Display panel. So a three-Zone Span on Display A is drawn as Zones {1,2,3} of Display B while the cursor skims B, and nothing stays drawn on A. AC-085 (LOCKED-SPEC.md:555-558): 'A three-Zone Span on Display A stays drawn dimmer while the cursor skims Display B'. T22 ledger line 9 ('blocker ... NOT fixed in T22') and T26 ledger line 3 ('KNOWN LIMIT') record it; CONTRACTS.md:284 still has a single-display Highlight, no amendment. Only one Display on this machine: traced in code, not observed.
- Repro: Scratch test: ArmContext with Displays A and B, each with a 3-Zone layout; SpanState(zones: [1,2,3], display: A, frozen: false, suspended: false); cursor = SpanLogic.Cursor(display: B, hit: .zone(1)); let span2 = SpanLogic.accumulate(span, at: cursor, flags: spanModifierDown, config); let h = SpanLogic.drop(at: cursor, span: span2, in: ctx).highlight -> h.display == B, h.secondary == [1,2,3]; OverlayModel.apply(h) paints B's Zones 1-3 secondary and A's Zones all idle.
- Fix hint (verifiers agreed 3/3): Give Highlight a per-Display secondary (e.g. secondaryDisplay: DisplayKey? or [DisplayKey: Set<Int>]) and let OverlayModel.apply paint the secondary set on span.display's panel.
