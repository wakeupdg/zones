# T32: Settings window shell: placement on the cursor Display, General pane, About pane, Launch at Login toggle with SMLoginItemService

Kind: build. Blocked by: T29 (shell models), T11 (BundleInfo, Diagnostics), T08 (spikes SPK-011, SPK-014). Estimate: 140000 tokens. Branch: ticket/T32. Modules: ZonesWindowing (Shell/, Adapters/) plus App/Settings (SwiftUI/AppKit, wiring only).

## Goal

1. A SwiftUI Settings window, hosted in a resizable NSWindow, opens on the Display under the cursor, centered in that Display's visible frame (`WindowPlacement.settingsFrame`). From the menu it becomes key (typing lands); from the hotkey it orders front on the current Space and becomes key only where SPK-014's per-OS table says so.
2. Tabs in order: General, Layouts, Shortcuts, Appearance, Exclusions, About. General and About are filled here; the other four are one-line placeholder views that later tickets replace.
3. General shows the two status rows from `GeneralPaneModel`, the Activation and Span modifier key caps, a Re-run onboarding button, and the Launch at Login toggle. About shows version, build, signingIdentity, "MIT" and the single "inspired by FancyZones" line.
4. `LoginItemToggleModel.derive` is pure: on only for `enabled`; caption plus Login Items button for `requiresApproval` and `notFound`; the signed-release caption for `invalidSignature`. Registration happens only on a user action; status is re-read on appear and on app activation.
5. `SMLoginItemService` wraps `SMAppService.mainApp` behind `LoginItemService`. Activation policy stays accessory (ADR-0019); never call `setActivationPolicy`.

public protocol LoginItemService: Sendable {   // Production: SMLoginItemService. Fake: FakeLoginItemService

public struct AboutModel: Hashable, Sendable { public var version, build, signingIdentity, license: String; public var attribution: String  /* exactly one line containing "FancyZones" */ }

public struct DisplaySnapshot: Hashable, Sendable { public var key: DisplayKey; public var frame: CGRect; public var visibleFrame: CGRect; public var scale: Double

// SMLoginItemService has no declaration in CONTRACTS; shape it as:
public struct SMLoginItemService: LoginItemService { public init() }   // @MainActor members over SMAppService.mainApp

## Test plan

Swift Testing, red then green, one slice per commit. Write the test first, watch it fail for the right reason, then implement.

1. `WindowPlacementTests.opensOnCursorDisplay` (AC-022; contract `WindowPlacement`). Build two `DisplaySnapshot`s: A at origin and B offset (for example B visibleFrame origin (1512, 25), size 2560x1415, menu bar excluded). With the cursor point on B: `cursorDisplay` returns B; `settingsFrame(cursor: B, size:)` has the same midX/midY as B.visibleFrame and lies inside it; an oversized `size` is clamped into visibleFrame; `editorFrame(cursor: B) == B.visibleFrame`; `NSWindow.StyleMask(rawValue: settingsStyleMaskRaw)` and the editor mask both contain `.resizable` (the test file may `import AppKit`). Repeat with the cursor on A to prove it follows the cursor. A cursor on no Display falls back to the main Display.
2. `LoginItemToggleTests.derivationTable` (AC-027; contract `LoginItemToggleModel`). Table-driven over (status, error) with exact expectations:
   - enabled, nil: isOn true, caption nil, button false, disabled false.
   - notRegistered, nil: isOn false, caption nil, button false.
   - requiresApproval, nil and notFound, nil: isOn false, caption "Zones is turned off in Login Items", button true.
   - any status, error `.launchDeniedByUser`: same caption and button true; isOn still comes from status.
   - any status, error `.invalidSignature`: caption "This build isn't properly signed; launch-at-login works in the signed release from /Applications", button false.
   - any status, error `.other(msg)`: caption is msg, button false.
   - `disabled` is false in every row (never disable on notFound). Error beats status for caption and button; status alone decides isOn.
3. Same test file, second slice: `LoginItemToggleTests.registerOnlyOnUserAction` (AC-027, "no register call at launch" and "turning on from notFound calls register"; consumes `FakeLoginItemService`). Building the coordinator and calling `refresh()` leaves `calls` with zero register calls. With status `notFound`, `setOn(true)` records exactly one register and then re-reads status. With a queued `.invalidSignature` throw, `setOn(true)` leaves the model off with the signed-release caption. `setOn(false)` calls unregister. `refresh()` re-reads status and clears the stored error. `already registered` never reaches the model (adapter maps it to success).
4. `AboutModelTests.fieldsAndSingleAttributionLine` (AC-029; contract `AboutModel`). From a `BundleInfo(version: "1.2.3", build: "45", signingIdentity: "ad-hoc", macOS: "15.0")`: version, build and signingIdentity equal the bundle's; `signingIdentity` also equals `Diagnostics.report(bundle:...)` `.signingIdentity` for the same `BundleInfo` (build the report with the same minimal arguments T11's tests use); `license == "MIT"`; attribution contains no newline; joining the five fields and counting "FancyZones" gives exactly 1.
5. No test: `SMLoginItemService`, SettingsWindowController, the SwiftUI views (swift test cannot drive AppKit UI, LESSONS). Implement, then confirm by build. Manual ACs: AC-023 (menu key, hotkey order-front/key per SPK-014), AC-028 (clean-account login item), AC-030 (About in light and dark). Add one ledger line per manual AC saying "implemented, awaiting human run".
