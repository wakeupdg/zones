# T63: Control-drag shows no Overlay for Gemini windows

Kind: fix (v0.1.1, from DG's manual QA on 2026-10-24). Blocked by: none.

## Evidence
- DG: a Control-drag snaps for most apps but not for Google Gemini (`com.google.GeminiMacOS`). Symptom (DG, 2026-10-24): **no Overlay** at all.
- AX facts (orchestrator probe): the Gemini window is a standard window, layer 0, position and size settable.
- Zones writes no drag/snap lines to the unified log (subsystem "Zones" empty, even with `--debug`), so diagnosis needs `scripts/qa/dragprobe.swift` (see docs/qa/logs/ac023-* for its output) or a new debug log line.
- Tester settings: Activation = Control, Span = Command.

## Goal
1. Find why the drag of a Gemini window never starts the Overlay (drag-start detection, window hit-test `element(at:)`, exclusion rules, app/bundle filters, or a Gemini-specific window property such as a custom title bar / non-standard drag). Evidence first; ask DG to do the drags you need, in short ordered steps.
2. Fix it test-first in the right layer, so that Gemini and windows like it snap.
3. If the useful fix is in `Sources/ZonesWindowing/Adapters/AXObserverBridge.swift`, `AXWindowSystem.swift`, `EventTapInputSource.swift` or `Seams/InputSource.swift` (T64 owns them now), STOP and report to the orchestrator before you edit them.

## Acceptance
- DG confirms: Control-drag of a Gemini window shows the Overlay and snaps. A second app with the same trait (if found) too.
- No regression: `swift test` green; Debug xcodebuild green.
